28/*
29* This file contains the 'hwinfo' API's for common devices and their attributes.
30* Processor architecture specific device API's are contained in a corresponding
31* <cpu arch>/hwinfo.h file (ex. ppc/hwinfo.h) while processor/family specific
32* device API's are contained in a hwinfo_<cpu>.h file (ex. hwinfo_85xx.h).
33* (Note that the latter naming is used because we currently don't break down
34* startup lib the files into 'cpu' specific directories, for example
35* ppc/85xx/hwinfo.h although in the future we may want to)
36*
37* For each supported device, all of the common attribute tags are created as well
38* a the tags specific to the device class. In order to remain portable and
39* flexible without over complicating the interface, some of the created tags are
40* not actually initialized to specific values. This is true for tags which may
41* have multiple instances for the particular device but the number of instances
42* would be device, board or cpu specific, for example the number of interrupt
43* vectors for a given ethernet device.
44*
45* To accomodate this, instead of trying to implement a variable sized data
46* structure which passes in all of the attribute values for all of the instances
47* of a particular attribute tag, instead the interface allows the caller to
48* specify for such attributes the number of tags to be created. The caller can
49* then initialize each of those tag instances with device, board or cpu specific
50* and/or calculated values after the entry is created. In this way, we also only
51* create the number of attribute tags we need for a given board.
52*
53* Implementation Note
54*
55* Note that this implementation (ie. placeholder tags) is a result of the fact
56* that when tags are scanned starting from a specific device offset, it is
57* assumed that the tags belonging to that device, follow that device. It's a bit
58* clumsy but that's the way it was originally implemented. There is no way to
59* validate that a tag belongs to a specific device (ie. item) since there is no
60* owner field for tags and therefore the assumption is that the tags belonging
61* to a device follow it and this is why all tags must be created at the time
62* the device is created.
63*
64*/
65

113/*******************************************************************************
114* hwidev_add_enet
115*
116* Adds an 'hwinfo' entry for a ethernet device.
117* Added attribute tags are as follows...
118*
119* - common attributes
120* - mac address
121* - phy address (1 per phy)
122* - input clock (1 per possible source)
123*
124* Unset tag fields should be set in the BSP init_hwinfo() and/or init_intrinfo()
125* functions.
126*
127* Note that when the <num_phys> PHY attributes for the ethernet device are
128* created, addresses are assigned to the PHY's in sequential order starting at
129* 0. The board configuration is responsible for ensuring PHY addresses are
130* correct for the given NIC
131*
132* Also, if the mac[] field is all zeros, the NIC address attribute tag WILL NOT
133* be added. This is the default (ie. no tag unless the BSP specifies a non zero
134* mac[] value). This is desireable so that if the BSP cannot fill in a sensible
135* value (from an EEPROM or some other source), the NIC address tag will not
136* added and hence not found by the driver. The driver will then resort to its
137* own scheme to set a NIC address, including the use of any command line
138* arguments.
139*
140* Returns: the offset in the hwinfo section of the added device or HWI_NULL_OFF
141* on error
142*/
143typedef struct
144{
145 hwiattr_common_t common;
146 uint8_t mac[6];
147 unsigned num_clks;
148 unsigned num_phys;
149} hwiattr_enet_t;
